# TDD Strict Mode

テスト駆動開発を強制するスキル。RED-GREEN-REFACTOR サイクルを厳格に適用します。

---

## The Iron Law

> **NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST**
>
> 失敗するテストなしに本番コードを書いてはならない

### 違反時の対応

| 違反パターン | 対応 |
|-------------|------|
| テスト前にコード作成 | **該当コード全削除** → テストから書き直し |
| テストが即座にパス | RED Phase 失敗 → **やり直し** |
| 「今回だけ」の例外要求 | **認めない** |
| 参照用にコード保持 | **認めない**（削除必須） |

---

## RED-GREEN-REFACTOR サイクル

### 🔴 RED Phase: 失敗するテストを書く

```
目的: 「何を作るか」をテストで表現する

1. テストファイルを作成/開く
2. 1つのテストケースを書く（最小限）
3. テスト実行 → 失敗を確認
4. 失敗理由が「機能がない」であることを確認
   - ✅ 正しい失敗: "function not found", "undefined"
   - ❌ 間違った失敗: syntax error, import error
```

**詳細**: [references/red-phase.md](references/red-phase.md)

### 🟢 GREEN Phase: テストを通す最小限のコードを書く

```
目的: テストを通す「だけ」のコードを書く

1. テストを通す最小限の実装を書く
2. 「動く」ことだけを目指す（美しさは後）
3. テスト実行 → 全パスを確認
4. 既存テストも壊れていないことを確認
```

**詳細**: [references/green-phase.md](references/green-phase.md)

### 🔄 REFACTOR Phase: コードを整理する

```
目的: テストがグリーンのまま、コードを改善

1. 重複を除去
2. 命名を改善
3. 構造を整理
4. テスト実行 → まだグリーンであることを確認
5. コミット
```

**詳細**: [references/refactor-phase.md](references/refactor-phase.md)

## 実行フロー

```
タスク開始
    │
    ▼
┌─────────────────────────────────────┐
│  🔴 RED: テストを書く                │
│  ─────────────────────────────────  │
│  1. テストファイル作成               │
│  2. 1つのテストケース作成            │
│  3. テスト実行                       │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│  ✅ 失敗確認                         │
│  ─────────────────────────────────  │
│  - 正しい理由で失敗しているか？       │
│  - YES → GREEN へ                   │
│  - NO → テスト修正                   │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│  🟢 GREEN: 最小実装                  │
│  ─────────────────────────────────  │
│  1. テストを通すコードを書く          │
│  2. テスト実行                       │
│  3. 全パス確認                       │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│  🔄 REFACTOR: 整理                  │
│  ─────────────────────────────────  │
│  1. コード改善                       │
│  2. テスト実行（グリーン維持）        │
│  3. コミット                         │
└─────────────────────────────────────┘
    │
    ▼
  次のテストへ（または完了）
```

## TDD が必須の場面

| 場面 | 必須度 | 理由 |
|------|--------|------|
| **新機能実装** | ★★★ | 設計をテストで表現 |
| **バグ修正** | ★★★ | 再現テストで回帰防止 |
| **リファクタリング** | ★★★ | 既存動作の保証 |
| **API 変更** | ★★★ | 契約の明示 |

## TDD 例外（明示的な許可が必要）

| 場面 | 理由 |
|------|------|
| 設定ファイル | ロジックなし |
| 生成コード | 自動生成のため |
| 使い捨てプロトタイプ | **ユーザーが明示的に許可した場合のみ** |

## テスト品質基準

### 良いテストの特徴

| 特徴 | 説明 |
|------|------|
| **1テスト1アサーション** | 失敗時に原因が明確 |
| **説明的な名前** | `test_user_can_login_with_valid_credentials` |
| **実コード優先** | モックは最小限に |
| **エッジケース網羅** | 境界値、空、null |
| **独立性** | 他のテストに依存しない |

### 避けるべきパターン

詳細: [references/anti-patterns.md](references/anti-patterns.md)

## よくある言い訳と回答

| 言い訳 | なぜ無効か |
|--------|----------|
| 「後でテスト書きます」 | 後からのテストは実装を検証するだけ。設計を駆動しない |
| 「手動テストしました」 | 再現性がない。CI で回せない |
| 「時間がない」 | TDD は長期的に時間を節約する |
| 「このコードは単純」 | 単純なコードほどテストも単純。書かない理由にならない |
| 「参考にしたいだけ」 | テストなしのコードは技術的負債 |

## VibeCoder 向けガイド

TDD は「難しい技術」ではありません。**「成功基準を先に決める」** だけです。

```
従来の進め方:
  作る → 動くか確認 → 直す → 確認 → ...

TDD の進め方:
  成功の定義 → 作る → 成功確認 → 次へ
```

### 例: メール送信機能

```
❌ 従来: 「メール送信機能を作って」→ コード書く → 手動で送信テスト

✅ TDD:
  1. 「メール送信が成功したらtrueが返る」テストを書く
  2. テスト実行 → 失敗（まだ機能がない）
  3. 機能を実装
  4. テスト実行 → 成功
  5. 「無効なアドレスならfalseが返る」テストを書く
  6. ...繰り返し
```

## 設定

```yaml
# .claude-code-harness.config.yaml
tdd:
  mode: "strict"  # default: strict
  # "off" - TDD 言及なし
  # "recommended" - 推奨のみ（強制しない）
  # "strict" - 強制（デフォルト）
```

無効化する場合:
```yaml
tdd:
  mode: "off"
```
