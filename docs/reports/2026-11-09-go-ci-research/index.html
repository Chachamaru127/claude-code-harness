最近の方向は「実測して配分する」

公式資料で確認できる設計の方向を整理した。業界全体の採用率を調べた統計ではない。

方向何が変わるか今回の採否
実行時間でテストを分割ファイル数を均等にするだけでなく、時間の長い処理を別の実行先へ配る。CircleCIは空いた実行先に残りを配る動的分割も提供。公式資料考え方を採用。まず単純な2分割を候補にする。別サービスや動的な配分機構の導入は保留。
実行環境を毎回作り直す前のジョブが残した状態を持ち越さない。Instaboxはジョブごとに新しいマシンを作る。公式資料現行方式を維持。消えるマシンの診断ログを残す方法を確認する。
変更の影響からテストを選ぶ変更ファイルだけを見る方法より、利用関係まで調べる方法の方が対象を広く拾える。関連機能の案内今回は全テストを優先。この規模で精密な選択機構を作る費用に見合う証拠はない。
準備の再利用依存物とコンパイル結果をキャッシュし、毎回の準備を減らす。setup-go公式既に導入済み。新設せず、実際のcache hitと準備時間を測る。

PRを出すと、全パッケージを複数のInstaboxジョブに配る。すべて成功したときだけ既存の必須チェックを成功にする。

2分割は初期案で、実測後に配分を決める。パッケージ数ではなく所要時間をそろえる。単独で重いパッケージがあるなら、その内部のテストや起動する子プロセスを調べる。

速くなる仕組みと限界

実測値ではない。2台が同時に始まり、均等に分割できると仮定した図。実際は起動、コンパイル、待ち時間が加わる。合計の処理量は減らず、費用が半分になる意味でもない。

GitHub Actionsの matrix でジョブを分け、max-parallel で同時数を制限できる。GitHub公式

実装するときの順番

  1. 通信断を記録で切り分ける。対象commit、Goバージョン、OSイメージ、コマンド、キャッシュ状態をそろえる。ランナーの Runner_ / Worker_ ログと、マシンのメモリ、CPU、停止時刻を照合する。
  2. 契約済みの範囲で分割を試す。全一覧と割当一覧を照合し、抜けを検出する。初期案は2ジョブ、同時2。各ジョブ内の同時実行を抑える -p 1 -parallel 1 を基準に計測する。サイズと同時実行枠はアカウントの実値で確かめる。
  3. 同じcommitの全結果で合否を決める。失敗、キャンセル、必要なジョブのskipを成功扱いしない。既存の必須チェックは、同等以上の検査へ移すまで残す。
  4. 遅い箇所だけ直す。分割しても同じテストで止まるなら、テスト側を調査する。メモリ不足ならサイズ変更を検討。通信やマシン終了が原因ならInstabox側の診断につなぐ。

GitHubは _diag の診断ログと、使い捨てランナーのログの外部保存を案内している。マシン自体が消えた場合、ジョブ末尾のアップロードだけではログを回収できない。既存の保存経路とInstabox側の取得可否を先に確認する。GitHub公式

Go特有の注意点と、先の説明の訂正
  • -p はビルドやテストバイナリの同時実行数。-parallel は主に t.Parallel を使うテストの同時数。両方を1にしても、テストが自分で起動する子プロセスやgoroutineをすべて1つに制限するわけではない。
  • -timeout の既定10分はテストバイナリ単位。GitHubジョブ全体の制限とは別。約11分で通信断になったことから、Goの10分制限が原因とは断定できない。
  • -count=1 はテスト結果のキャッシュを使わず再実行する指定。ビルドキャッシュまで全部無効にする指定ではない。

CI仕様 / 制限と実行環境

判断の基準

全パッケージを実行できたか、通信断の理由を説明できるか、既存の費用と権限で運用できるか。この3点で比較する。高速化率や完走率は、まだ測っていない。

推奨への確信度は中程度。公式に支えられた一般的な構成だが、このrepoの最も重いテストと通信断原因が未確定だからだ。固定の観測日数は置かず、同じ条件での実行記録と、失敗時にmergeを止める動作を確認する。

本人が押さえるのは「全テストの範囲を維持する」「上位契約へ進む条件」の2点。パッケージの配分、ログの収集、既存チェックへの接続は実装側が詰める。workflowの差分は戻せるが、消費済みの実行時間や料金は戻らない。
