04 — Judgment

押さえる本質と、着手判断

押さえる本質: 今回の設計判断は 7 本 (D62-D68) を decisions.md に Why つきで記録済み。特に効くのは 3 つ — ①縮退は fail-visible (止めずに可視化して判断を倒す) ②データ駆動ルールの強制力上限は ask、deny は人間 only ③LLM はビルド時、実行時は決定論、信頼するのは実行記録。
AI に任せてよい詳細: 各 handler の実装、テスト fixture、hooks 配線、mirror 同期。

A. PR を作って main へ (推奨)
+ APPROVE 済み・全ゲート緑で寝かせる理由がない。+ Phase 138 が 135.4 に依存しており、merge しないと次の弾が積めない
− merge 後も稼働セッションに効くのは release + plugin 更新後 (もう 1 手必要)
B. branch のまま保留
+ 追加で見たい観点があれば再レビューを積める
− main が進むと conflict リスクが増える。− 検証チェーンが効かない期間が延びる
判定
Phase 134-137 は完了、レビュー APPROVE。今回の依頼の芯だった「検証がオナニーにならない仕組み」は、入口・中間・出口の 3 点で機械的に担保される形になった。推奨アクション: PR 作成 → merge 後、次スプリントで Phase 138 (汎用 feedback ルール = 「同じ指摘を二度させない」の一般化) に着手。
正直な但し書き
  • merge しても稼働中セッションの hook は installed plugin の古い binary を使う (過去実測)。実効化には release + plugin 更新が必要。
  • writing lint の辞書は空の状態から始まる。育つのは立花が指摘 → 承認してから。既定 off (config で opt-in)。
  • blind 評価 (137.2) は説得系/文書系のみ発動。機能系タスクでは何も変わらない (意図した設計)。
  • レビュー 2 回目の指摘どおり、初回実装の RED 実測記録の一部は squash により repo 内から辿れない (GREEN は全部再実行で確認済み)。今後は tdd-red-log への永続化を推奨される。
  • 今回のセッションで露呈した運用課題 2 件は別途対処済み/起票済み: worker の rm ask 連発 (worker 契約 NG-4 追加 + work-mode) と、監視が session limit を ask 待ちと誤診した件 (通知 4 回のうち後半 2 回は誤報)。
