# Harness Plan

The integrated planning skill for Harness.
Consolidates the following three legacy skills:

- `planning` (plan-with-agent) — turning ideas into Plans.md entries
- `plans-management` — task state management and marker updates
- `sync-status` — syncing Plans.md with implementation state

## Quick Reference

| User input | Subcommand | Action |
|------------|------------|--------|
| "create a plan" / `/harness-plan create` | `create` | Spec delta / skip reason → Plans.md task generation |
| "add a task" / `/harness-plan add` | `add` | Add a new task to Plans.md |
| "mark complete" / `/harness-plan update` | `update` | Change task marker to cc:done |
| "where are we?" / `/harness-plan sync` | `sync` | Compare implementation with Plans.md and sync |
| `/harness-sync` | `sync` | Progress check (equivalent to the standalone sync surface) |
| `/harness-plan create` | `create` | Create a plan with the spec.md / Plans.md dual-contract |
| `/harness-plan list` | `list` | List named Plans from `plans/manifest.json` |
| `/harness-plan switch <name>` | `switch` | Save the active plan to `.claude/state/active-plan.json` |

## Literal companion commands (CC 2.1.108+)

- `/recap`: Re-fetch a summary after returning to a session after a long absence, then enter `sync`
- `/undo`: Alias for `/rewind`. Use as-is when you want to immediately revert the last plan update

## Subcommand details

### Standard plan quality contract

See [references/planning-quality.md](${CLAUDE_SKILL_DIR}/references/planning-quality.md)

`harness-plan` is the planning surface that produces the co-required planning output for the spec.md product contract and the Plans.md task contract.
The precedence `spec.md > sub-spec > Plans.md` is maintained.
Plans.md is the task ledger; the root `spec.md` is the product contract. This hierarchy must not be broken.
Do not convert user-provided information directly into Plans.md as-is.
For plan creation or large task additions, verify the latest information, existing specs, memory, and multi-perspective discussions,
then convert only the elements that should be incorporated into this product into the task contract.
`/harness-plan create` returns a `Spec delta` or `Spec skip reason` together with `Plans.md` task generation.
The output must always include either a `Spec delta` or a `Spec skip reason`.
`Spec delta` / `Spec skip reason` are generated by Harness; the consumer only approves or revises them.

**When to apply**:

- Creating a new plan with `create`
- Adding a task with `add` that affects product behavior / API / permissions / billing / external integrations / distribution surfaces
- The user provided an external product, a competitor, a spec proposal, an improvement, or a comparison
- There is a risk of conflict with existing specs or past decisions

**When it is acceptable to treat lightly**:

- `update` that only changes markers
- `sync` that only reconciles status
- typo, format, README/CHANGELOG only
- Narrow changes where the correct outcome is already fixed by existing specs and tests

**Quality flow**:
1. Decompose the input, explicitly identifying what is being evaluated, the scoring axes, and uncertain facts
2. Fetch the latest information. Prefer WebSearch / official documentation / primary sources for external facts; cross-check important points with multiple sources
3. Verify existing specs, root `spec.md`, Plans.md, README, docs, CLAUDE.md, and related skills
4. Check available memory surfaces (harness-mem / harness-recall / `.claude/agent-memory/` / `.claude/state/`) with project scope
5. Use Task sub-agents to run independent reviews from different perspectives: Product / Architecture / QA / Skeptic
6. Produce a neutral scoring review and classify as Required / Recommended / Optional / Reject
7. Report the proposal, its rationale, and expected outcomes in `$easy` format
8. Translate only the accepted proposals into root `spec.md` / Plans.md / test tasks

### create — plan creation

See [references/create.md](${CLAUDE_SKILL_DIR}/references/create.md)

Gather ideas and requirements through conversation, then generate an actionable Plans.md.

**Flow**:
1. Check conversation context (extract from recent discussion or start fresh)
2. Ask what is being built (max 3 questions)
3. **Quality flow check** (latest info, existing specs, memory, multi-perspective review, scoring)
4. Technical research (WebSearch)
5. Extract feature list
6. **spec.md / Plans.md dual-contract check** (Spec delta or Spec skip reason + Plans.md tasks)
7. Priority matrix (Required / Recommended / Optional / Reject)
8. TDD adoption decision (test design)
9. Generate Plans.md (with `cc:TODO` markers)
10. Guide to next actions

### spec.md / Plans.md dual-contract check (default)

Plans.md is the task contract for "what must be done"; the root `spec.md` is the product contract for "what is correct".
Co-required planning output means both outputs are required; the precedence `spec.md > sub-spec > Plans.md` is maintained.
When implementation may drift, update the root `spec.md` before generating Plans.md.
`create` and product-impacting `add` always read the root `spec.md`.

Priority for where to save:

1. Root `spec.md`
2. Only when no root `spec.md` exists in the consumer repo: an existing project spec / architecture / product compass
3. Only when no root `spec.md` exists in the consumer repo: `docs/spec/00-project-spec.md`
4. In repos that already have a spec convention, follow that convention's spec path

Conditions where creation/update is required:

- A task that determines user-visible behavior, APIs, data models, permissions, billing, or external integrations
- A task with multiple implementation approaches where the choice changes product behavior
- A task where past or current conversation shows signs that spec ambiguity caused implementation drift
- Plans.md has the work, but there is no stable document that defines the correct outcome for the project

Conditions where it is not required:

- typo, format, dependency bump, README/CHANGELOG only
- Narrow refactor with no behavior change
- A fix where existing specs and tests sufficiently fix the correct outcome

Output contract:

- `Spec delta`: When updating the product contract, write the target spec path and the changes
- `Spec skip reason`: When not updating the product contract, write the reason
- `Spec delta` / `Spec skip reason` are generated by Harness; the consumer only approves or revises them
- Even for docs-only / mechanical tasks, leave a `Spec skip reason` in the task context / sprint contract
- Do not conclude that a missing search result, unavailable memory, or unread file means it is absent. `not_observed != absent`
- Do not ask the user to write a spec from scratch. The agent drafts the minimal delta from the existing spec and input, and only presents decision branches when genuinely ambiguous

Reference:

- `docs/plans/spec-ssot.md`

### Session launch guidance after create completes (required)

When `create` finishes, do not end with only an explanation — always provide both the **new session launch command** and the **first input to type immediately after launch**.

Priority order:

1. Only one incomplete task, or it is natural to start with just the first one
   - Launch command: `claude`
   - First input: `/harness-work <task number>`
2. Multiple tasks with loose dependencies where running them together is natural
   - Launch command: `claude`
   - First input: `/breezing all`
   - Alternative: `/harness-work all`
3. Long-running tasks or tasks that require re-entry
   - Launch command: `ENABLE_PROMPT_CACHING_1H=1 claude`
   - First input: `/harness-loop all`
   - Alternative: `/breezing all`

Include at least these 3 lines:

- `New session launch command:`
- `First input after launch:`
- `Best for:`

Example:

```text
New session launch command: claude
First input after launch: /breezing all
Best for: Phase 1 has multiple tasks and it is more natural to run them together
```

When recommending a long-running approach, also include the Claude Code session launch command:

```text
New session launch command: ENABLE_PROMPT_CACHING_1H=1 claude
First input after launch: /harness-loop all
Best for: Long-running tasks that involve waits over 5 minutes or span multiple resumes
```

Notes:

- `scripts/claude-longrun.sh` is a development helper script for this repository and is not distributed to consumer environments after plugin installation
- Therefore, in guidance for consumers, always prefer the single-line `ENABLE_PROMPT_CACHING_1H=1 claude` command
- When only doing local development in this repository, `bash scripts/claude-longrun.sh` is acceptable on a local checkout

**CI mode** (`--ci`):
No interviewing. Uses the existing Plans.md as-is and only performs task decomposition.

### add — add a task

Add a new task to Plans.md.
For product-impacting additions, output a `Spec delta` or `Spec skip reason` in addition, following the "spec.md / Plans.md dual-contract check" above.

```
/harness-plan add task name: detailed description [--phase phase-number]
```

Tasks are added with the `cc:TODO` marker.

### update — update markers

Change a task's status marker.

```
/harness-plan update [task name|task number] [WIP|done|blocked]
```

Marker mapping:

| Command | Marker |
|---------|--------|
| `WIP` | `cc:WIP` |
| `done` | `cc:done` |
| `blocked` | `blocked` |
| `TODO` | `cc:TODO` |

### sync — progress sync

Compare the implementation state with Plans.md and detect and apply differences.

See [references/sync.md](${CLAUDE_SKILL_DIR}/references/sync.md)

**Flow**:
1. Get the current state of Plans.md
2. Detect Plans.md format (v1: 3 columns / v2: 5 columns)
3. Get implementation state from git status / git log
4. Check agent trace (`.claude/state/agent-trace.jsonl`)
5. Detect differences between Plans.md and implementation
6. Propose automatic corrections for stale markers
7. Present next actions

**Retrospective** (default ON):
If there is at least one `cc:done` task, automatically run a retrospective.
Analyzes estimate accuracy, blocker patterns, and scope changes, then records the learnings.
Can be explicitly skipped with `sync --no-retro`.

### team mode / issue bridge

Keep Plans.md as the source of truth; use GitHub Issue integration only in opt-in team mode.

- Do not use the bridge in solo development
- Team mode creates one tracking issue and generates sub-issue payloads for each task as a dry run
- `scripts/plans-issue-bridge.sh` never actually updates GitHub — it always returns dry-run payloads
- This bridge does not change Plans.md

Reference:

- `docs/plans/team-mode.md`

### named Plans

When using multiple Plans.md files, treat `plans/manifest.json` as the source of truth and select by name.

```bash
scripts/plan-registry.sh list
scripts/plan-registry.sh switch roadmap
scripts/plans-issue-bridge.sh --plan roadmap --format markdown
node scripts/generate-sprint-contract.js --plan roadmap 9.1.1
```

Operating rules:

- Use only one named plan per run
- In long-running / CI / issue bridge contexts, pass `--plan <name>` rather than relying on the active pointer
- Manifest paths are relative to the project root only. Absolute paths, `..`, and out-of-repo symlinks are rejected

- `docs/plans/named-plans.md`

## Plans.md format conventions

### Format

```markdown
# [Project Name] Plans.md

Created: YYYY-MM-DD

---

## Phase N: Phase Name

| Task | Description | DoD | Depends | Status |
|------|-------------|-----|---------|--------|
| N.1  | description | Tests pass | - | cc:TODO |
| N.2  | description | lint errors 0 | N.1 | cc:WIP |
| N.3  | description | Migration runnable | N.1, N.2 | cc:done |
```

**DoD (Definition of Done)**: Write a verifiable completion condition in one line. "Looks good" or "works properly" are prohibited. Make it decidable with Yes/No.

**Depends**: Dependencies between tasks. `-` (no dependency), task number (`N.1`), comma-separated (`N.1, N.2`), or phase dependency (`Phase N`).

### TDD tags

Tasks in Plans.md can include a TDD decision tag in the description or DoD.

| Tag | Meaning | `tdd_required` inference |
|-----|---------|--------------------------|
| `[tdd:required]` | This task requires writing a failing test first | `true` |
| `[tdd:skip:<reason>]` | This task skips TDD with a stated reason | `false`, `skip_tdd_reason=<reason>` |

`<reason>` must not be empty.
Examples: `[tdd:skip:docs-only]`, `[tdd:skip:no-test-framework-detected]`.

When there is no tag, `tdd_required` is inferred in the following order:

1. Plans.md tag: `[tdd:required]` / `[tdd:skip:<reason>]`
2. Files: required if the task involves source implementation in `src/`, `app/`, `cmd/`, `lib/`, `pkg/`, `internal/`, `go/`, etc.
3. Scaffolder inference: not required with a skip reason if the task is docs-only or has no test framework detected

### optional briefs / manifest

`harness-plan create` only attaches a brief when necessary. A brief is a supplementary document that briefly fixes the preconditions for implementation; it does not replace Plans.md or the spec SSOT.

- A project spec SSOT is a document that fixes the correct conditions for the whole project and is created only when needed
- UI tasks get a `design brief`
- API tasks get a `contract brief`
- When both UI and API are mixed, use separate briefs
- The skill frontmatter catalog can be exported as machine-readable JSON with `scripts/generate-skill-manifest.sh`

Reference:

- `docs/plans/briefs-manifest.md`
- `docs/plans/spec-ssot.md`

### Marker list

| Marker | Meaning |
|--------|---------|
| `pm:requested` | Requested by PM |
| `cc:TODO` | Not started |
| `cc:WIP` | In progress |
| `cc:done` | Worker work complete |
| `pm:approved` | PM review complete |
| `blocked` | Blocked (reason must always be stated) |
